# AI4Edu 面试演示

演示入口：<http://127.0.0.1:18000/demo/>。本机启动命令见 [运行手册](functional-runbook.md)。标准 Compose 部署使用8000端口。代码仓库不包含学生试卷、参考分、数据库和模型密钥；新机器需要自己的输入和凭据。

项目定位为一个可追溯、可评测的多模态评分工作流。当前演示正常朝向、完整的数学主观题输入，全自动执行，没有教师审核步骤。已有数据可以免费回放，新建单题会产生百炼调用费用。

## 能解释清楚的工程取舍

**评分流程有明确的数据契约。** 题目与参考解答先生成并校核共享细则。学生输入经过准备后，先独立转写，再结合图片、转写和固定细则逐项评分。程序检查评分点覆盖、证据是否存在、分数上限与精度，再用十进制累加总分。分数未知时保存为空，运行失败与学生真正空白分开记录。

**并发发生在考生、题目和长题图片分片之间。** 同一题仍保留转写后评分的依赖。FastAPI只负责提交与查询，PostgreSQL保存状态、检查点、结果和Outbox，Celery执行准备、评分与调度任务，Redis控制模型在途请求和速率。Worker中断后按租约恢复，成功阶段可以复用。供应商超时可能已经产生费用，所以不声称外部请求恰好执行一次。

**现场单题复用原有试卷。** `question_ids` 只创建所选题目的评分任务，整卷定位也只请求这些题号。细则与试卷累计预算不会因演示重新复制，批次预算在共享试卷预算之下继续约束并发调用。提交有幂等键，页面不会自动重发不确定的提交。

**模型和费用作为可观察的执行配置。** 每批次保存模型、提示词版本、思考开关和图像参数。当前B配置用Plus转写及评分、Max准备细则，只对评分开启4096 Token思考。费用按已配置参考单价和实际usage计算；未返回usage和未配置单价分别保留未知信息，最终账单以百炼为准。

**评测独立于评分。** 参考分只在结果保存后读取，不进入模型输入或执行快照。工作台展示本批次全部预期题目的±1分一致率、可判定率、MAE及失败数。不能只计算成功题来掩盖执行失败；MAE需同时说明是在可判定题上计算。标签必须对应实际上传的试卷、考生和题目，本地样例标签不能拿来评价其他输入。

**工作流的边界明确。** 当前主体是带模型角色、工具调用、持久化状态和校验器的固定工作流；风险复判是可配置分支。它没有自主制定长期计划或任意选择工具。面试时可以说明这些能力与Agent工程相通，但不要将固定流程描述成已经实现的完全自主Agent。

## 质量与规模的实测边界

- 正式B基线留出验收：31名首次运行考生、155题，可判定率85.16%，全量成功评分且误差≤1分为60.65%，可判定题MAE1.227分，15题执行失败。未通过预先确认的门槛。
- 正常图思考回归：4名考生20题，开启思考首次19题成功、1题HTTP400，显式重试后20题完成；最终MAE1.90分、±1分10/20，与关闭思考组相同。不能据此声称整体准确率提升。该回归和现场样例都已被查看，不能重新称为盲测。
- 已有参考数据主要是每题总分，无法验收每个数学步骤的给分正确性。证据可追溯和格式校验能帮助发现错误，无法保证数学判断正确。
- 1000名考生、5000题通过了使用模拟模型的真实队列全链路与故障恢复测试；真实百炼调用观测到模型并发16。尚无真实百炼1000人端到端吞吐结果，不能用模拟耗时估算上线时延。

更详细的数字见 [验证记录](verification.md) 和 [并发测试](concurrency-loadtest.md)。当前演示侧重正常输入，不把旋转等输入泛化当作已完成的质量保证。

## 如何介绍AI辅助开发

可如实说明代码实现、测试和部分审查使用了AI编码工具，并用实际需求、失败案例、冻结评测和浏览器实测验证结果。面试中只把自己能解释、能复现、确实做过的需求判断和验证工作作为个人贡献，不将自动生成代码或并行审查包装成独立手写的全部成果。

建议现场打开 `api.py` 的单题提交与预算复用、`pipeline.py` 的阶段依赖和检查点、`scoring.py` 的证据校验，以及真实失败和评测报告。能围绕一个错误解释数据、模型、校验和评测分别承担什么职责，往往比继续堆功能更有说服力。
