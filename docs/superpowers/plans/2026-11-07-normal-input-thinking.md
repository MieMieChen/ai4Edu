# 正常输入与评分思考模式

用户将当前范围收窄到正常朝向、完整清晰的输入，要求开启思考。使用现有配置能力，不修改图像泛化算法、不变更提示词或共享评分细则。

1. 核对百炼参数：Plus的max_tokens限制最终回答，thinking_budget单独限制推理；请求前费用与Token预留需要包含两者。
2. 运行已有模型请求、长题预算、批次配置冻结测试。现有实现符合要求时只调整配置，不新增适配层。
3. 从既有开发数据选择固定4名学生：初评名单前3名，以及已确认数学判断错误的回归学生。使用该试卷的固定栏位导出第15—19题完整图片，正常朝向，不按结果筛题。
4. 保存输入图片哈希、共享细则哈希、配置和预算。两组均使用同样的20张图片、同样的题目与细则；仅grade角色思考开关不同。转写独立运行，必须记录两组转写是否相同，不能把整条流程差异全部归因于评分思考。
5. 关闭思考基线使用当前API配置提交，预算4元。更新本机及示例配置：thinking_roles=["grade"]、thinking_budget=4096；历史任务执行快照保持不变。
6. 使用临时本地API端口18002读取新配置并提交思考组，预算4元；共用原PostgreSQL/Redis及Worker，执行快照确保两组思考参数互不影响。两组可同时并行处理，继续使用原50元试卷总预算。全部结束且模型请求清空后，停止临时API、平稳重启主服务使后续批次默认开启grade思考。
7. 检查实际响应reasoning_content的存在/长度及reasoning_tokens用量；只记录统计，不对外展示推理文本。导出全量首次结果、误差、费用和耗时，不自动重试。
8. 输出开发回归报告，说明20题小样本和已见标签的限制。确认服务新批次启用grade思考；验收未通过状态不因该开关自动改变。

复核：正常输入裁图仅用于这份数据集的实验适配，不作为通用网站版面定位算法。所有数据、模型输出、凭据保留本地；配置及说明可纳入代码仓库。
